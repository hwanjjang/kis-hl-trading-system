Test and smoke outcomes below cite the builder's and the local independent verifier's retained evidence (253 unit tests passing, 18 offline CLI smoke processes passing, 53/53 manifest hashes matching) and are not certified by me. No real venue order was required or assumed. Notification delivery is out of scope by user instruction.

What I confirmed works as claimed (evidence in code, not just reports):

- **Write-ahead attempts and no blind resend.** `_send` persists the row and an UNKNOWN attempt before any network call and swallows transport exceptions, leaving UNKNOWN authoritative (`kis_hl/managed_execution.py:326-354`). Regression `test_unknown_entry_is_not_resent` covers it.
- **Kill switch rechecked at the send boundary** after attempt creation (`managed_execution.py:330-337`) and after preflight (`:490-492`). Closes R2-1.
- **Strict native stop readback.** Coverage requires open, `kind=stop`, sell, reduce-only, `trigger_type=sl`, and a trigger at or above the floor (`managed_execution.py:594-605`); the HL gateway binds coin, oid/cloid, side, reduce-only and `Stop Market` and raises on mismatch (`managed_gateways.py:194-219`). Capability evidence refuses a "verified" native SL without those fields (`capabilities.py:33-42`).
- **KIS native stop refused** (`managed_gateways.py:680-681`); US paper sell disabled (`kis/client.py` diff line 3055-3056); POSTs never retried (`_request_with_auth`, method != GET returns once); cash orders are limit-only.
- **Stop execution price** is trigger times one minus slippage, rounded up to a valid tick, separate from the trigger (`managed_execution.py:636-647`), matching the documented SDK contract.
- **Ownership guards** block raw HL entries and legacy enrollment while a managed live owner exists, with a context-var permit for the supervisor's own entry (`managed_execution.py:21-48`; `hyperliquid/client.py:312-319`; `trailing_runner.py` diff).
- **Lock reentrancy.** `account_lock` is a thread-local RLock plus flock, so supervisor loop, `step`, and `cash_order`/`place_order` nesting is safe (`execution_lock.py:16-40`).
- **Journal ledger**: equal-time ordering by position continuity, correction supersession computed from the full effective set, fee not double-added, retention anchored by current `userFills`, append-only attribution enrichment that cannot be erased by unknown replay (`journal_sync.py:191-231, 289-314, 495-544`; `journal_history.py:88-103`). IV-1 and IV-2 fixes are present in source.
- **Scheduler lock released during idle** (`operations_cli.py:405-465`) with a real-subprocess regression.
- **Redaction** of account identifiers in account reads and instrument verification output; sanitized KIS errors.

**F1 reproduction in more detail.** Enqueue the fixture plan with the test `Gateway`, step to PROTECTED with `size = filled = "1"` and the stop filled-readback as in `test_intervention_flat_cleanup_still_cancels_owned_stop`. Replace `gateway.snapshot` with a function that raises `RuntimeError("KIS account inquiry failed")` once, then restores the original but returns `price="90"` (below the 96 floor). Expected by the spec: DEGRADED, then an exit request once fresh data returns. Observed by code path: state becomes INTERVENTION on the failing step; every later step takes the `size != 0` branch at `managed_execution.py:557-559` and returns without ticking the trail or requesting an exit. With `native_sl=False` the position has no protection at all.

**Items checked and not raised.** The concern that `_send` mishandles KIS results is unfounded: `cash_order` and `revise_cash_order` return dicts with `status`/`order_id`/`organization_id` (patch lines 3070-3075, 3108). Lock nesting is safe (re-entrant). HL `withdrawable` as available notional is conservative. The `ingest` enrichment branch has no stale-variable or NameError path across iterations. KIS session gating via the KR200/SP500 trade.xyz session groups resolves correctly. Grant reservation consumes a slot before enqueue and cannot exceed `max_intents`. `Signals.execute` fixes `intent_id` to the signal id, so one signal yields at most one intent per mode.

## Verdict and remaining rollout limits

**CHANGES_REQUIRED.** F1 is a HIGH robustness defect in the protection loop: it fails closed on orders, but it converts any single transient read error into an indefinite, human-gated unprotected state for local-SL positions, which PT5 and MV3 §4 define as bounded and degraded rather than terminal, and the operations document describes it inaccurately. F2 is a documentation and behavior mismatch on the live asset set that AGENTS.md treats as a safety-rule change. F3 and F4 should be fixed before the persistent worker or live KIS entries are relied on. Everything else is advisory.

No requirement violation was found in order transmission safety: previews and paper mode send nothing, live requires `--live` on both submit and supervisor, unknown outcomes are never resent, native KIS protection is refused, and stop readback cannot be satisfied by a generic stop label. The independent verifier's executed evidence for the frozen candidate (253 tests, 18-process smoke, hash match) is consistent with the source I read, and I did not find the earlier-closed findings C1–C9, R2-1, IV-1 or IV-2 reopened.

Controlled-rollout limits that remain true regardless of the fixes above, and that the documentation already states: live KIS order acceptance, cancellation reservation races, partial-fill and gap behavior, the KST interpretation of overseas quote clocks, HL native stop fills through gaps, and KIS journal finalization requiring statement import are all unverified offline and must be exercised in a supervised in-session rollout with small size before production reliance.
