## Dispositions

1. **Required: confirmed native-trail cancellation regression.**
   `managed_execution.py:849` treats every terminal native attempt as an exit
   trigger and stops examining later attempts. Attempts are ordered by insertion,
   so the original smaller native trail precedes the full-position overlay.
   In three stub scenarios (canceled/rejected/expired original trail), the overlay
   remained open and active for 1.5 units, but the supervisor recorded zero native
   coverage and submitted an exit for all 1.5 units. No price trigger or protective
   fill occurred. The defect warrants correction before merging.
   Technically the exit is a reduce-only IOC limit with bounded slippage, not an
   unbounded market order (`managed_gateways.py:365`). That distinction does not
   change the unwanted-exit finding.

   Assess all established native attempts before deciding whether a non-fill
   termination loses coverage. A remaining owned, active, valid-readback native
   order covering the entire residual position may satisfy coverage. Do not sum
   smaller independent trailing orders as a substitute for a full-size trail.
   Preserve the full-residual exit latch on any actual protective fill, and the
   immediate exit for a single terminated established trail or no valid full-size
   replacement. Do not recreate trails or reset watermarks. Preserve the distinct
   unknown/rejected initial-submission intervention semantics.

2. **Recommended: confirmed pre-submission availability issue, with a narrower fix.**
   `managed_execution.py:1088` marks a tranche REJECTED for a read-time OSError or
   RuntimeError. Recovery, SQLite reopen, identical authorization replay, and a
   later tick still produce zero add submissions. The same rejected tranche is
   returned. Existing protection is retained, so this is availability rather than
   duplicate-order or unprotected-exposure failure.

   Retain QUEUED only for classified transient read errors before a durable send
   attempt. Do not classify every RuntimeError as transient: the API client uses
   it for account/coin identity mismatch, unsupported response shapes and HTTP
   failures, while eligibility/configuration guards also use it. Check authority
   and expiry before retrying reads (currently gateway preflight precedes these
   checks), and revalidate every admission condition after recovery. Signed send
   UNKNOWN must remain non-retriable. Keep retries within the existing expiry and
   operational bounds; do not invent a second order lifecycle.

3. **Recommended defensive rejection: capital evidence ignores extra components.**
   `account_capital.py:27-42` processes only balances[].total. Injecting nonzero
   evmEscrows, balances[].borrowed, or balances[].supplied individually still
   yields total 1000, operating capital 10000, one-unit risk 100. This demonstrates
   the validation gap; it does not establish the correct monetary total or prove
   those combinations occur under a real unifiedAccount mode.

   The official spot API identifies spotClearinghouseState as the unified account
   source of truth, so the selected endpoint is appropriate. Its published sample
   does not define these additional fields or their unified-mode coexistence.
   Portfolio-margin documentation describes borrow/supply behavior, but that mode
   is already rejected here. Consequently, do not assert a demonstrated live
   over/under-sizing amount or add these fields blindly (risk of double counting).
   Reject nonzero or malformed unsupported collateral/liability components and
   contradictory mode evidence until their meaning is supported. This limited
   guard is appropriate for issue 27's ambiguous-reconciliation contract.
